# App Hub: outside-developer and store-readiness review

App Hub has a credible distribution foundation for OctoSense Card apps, but it is not yet a self-service app store. A developer can prepare a bundle and an operator can sign a catalog; the complete journey from a fresh developer machine to a useful, independently published, maintainable app is unfinished.

The immediate objective should be **a dependable store for free Card apps with an excellent developer workflow**. Native Rust/JNI apps currently require integration into a shell release. Supporting arbitrary native packages would be a separate distribution and runtime project, rather than another publishing screen. The Card-only constraint can be a valid product choice if its supported capabilities are sufficient and explicit.

Live GitHub reads confirmed an empty signed production catalog, sequence 4 dated 2026-09-20, and zero configured workflows in the Hub repository. The documented `OctoSense-org/publish-app` repository returned 404 to this session; this establishes that the advertised route was unavailable here, not that no private development exists. No applications were published and no application source was changed.

The baseline is lifecycle coverage, not copying another store's bureaucracy. Apple's developer workflow includes account roles, uploads, beta testing, review status and analytics. Google Play separates test tracks from production and supports controlled rollouts. Those are useful comparisons for what an outside developer eventually needs. [Apple workflow](https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-workflow), [Play releases](https://support.google.com/googleplay/android-developer/answer/9859348?hl=en), [Play testing](https://support.google.com/googleplay/android-developer/answer/9845334?hl=en), [Play staged rollouts](https://support.google.com/googleplay/android-developer/answer/6346149?hl=en).

**What already works**

The implementation includes signed manifests and catalogs, anchor-certified working keys, content digests, package admission, capability and quota policy, retained artifacts, catalog verification, local asset serving, install consent, search, app detail pages, screenshots, launcher identities and installed-app icons. The mobile integration adds a persistent catalog sequence floor, cached browsing, update detection, download staging, recovery from interrupted replacement, preservation of app data, and closure of running instances after successful updates. These are substantive building blocks, not merely mockups. [Hub client](../../crates/app-hub/src/client.rs), [mobile backend](../../../OctoSense-mobile/apps/app-hub/src/catalog.rs), [mobile integration guide](../../../OctoSense-mobile/apps/app-hub/README.md).

The following assessment credits the current mobile interface as well as the shared backend. Some functionality exists in the older standalone store but is absent from the newer mobile interface.

| Developer/user need | Current state | Gap and priority |
| --- | --- | --- |
| Install tools and start an app | Rust builds, sibling framework checkouts, metadata starter, linked authoring guides | P0: distributable SDK, managed runtime versions, runnable starter and one development command |
| Build useful app behavior | Card rendering, native widgets and policy primitives exist | P0: explicit app logic entrypoint, events/state/effects contract and tested service adapters |
| Claim and maintain an app | Publisher ID/key fields and signature checking | P0: verified ownership registry, namespace claims and correct key continuity; P1: teams, transfer and recovery |
| Submit without maintainer access | Manual preparation documented; operator `publish` command | P0: authenticated submission endpoint or bot, artifact upload, concrete working CI action |
| Pass review and understand failures | Deterministic gate and pluggable reviewer | P0: runnable-bundle checks and recorded review decisions; P1: status, notifications, resubmission and appeals |
| Discover and install | Search, categories, details, consent and installation | Mostly implemented for the current small catalog; P1: compatibility filtering and complete listing links |
| Update reliably | Update detection and mobile transaction/recovery mechanisms | P0: keep approved installed versions runnable; P1: beta channels, release targeting, rollback and migrations |
| Remove an app | Shared backend and older store support removal | P0: expose uninstall and data-deletion behavior in the current mobile UI |
| Operate distribution continuously | Static GitHub origin and signed catalog | P0: scheduled catalog renewal and protected release automation; P1: monitoring, recovery and scalable artifact delivery |
| Maintain quality after launch | Local instrumentation and logs | P1: consent-aware crash/error reporting, install failures, release health and developer feedback |
| Run a commercial marketplace | No commerce model found | P2: purchases, entitlements, subscriptions, refunds and developer settlement, if paid apps become a product requirement |
| Grow discovery and trust | Basic search and publisher-supplied metadata | P1: support/report links and moderation process; P2: ratings, developer replies, localization and richer discovery |

P0 means needed before inviting independent developers to rely on a public free-app store. P1 supports a sustainable public beta. P2 expands marketplace scope.

**Concrete release blockers**

1. **Publishing is still an operator workflow.** `hub publish` requires the Hub working signing key and a local catalog. There is no developer login, upload/submission command, publisher registry, submission status service, or repository workflow implementing the promised automatic merge. The scan only runs when `--reviewer` is supplied; `--reviewed` is an operator flag, not a recorded approval bound to a reviewer and bundle digest. The README's first-publisher/returning-publisher automation is therefore ahead of the inspected deployment. Keep the operator tool private and add a thin authenticated submission service or GitHub bot; developers should supply their artifact and provenance, never Hub credentials. [CLI publish](../../crates/app-hub/src/bin/hub.rs), [publishing guide](../PUBLISHING.md), [live repository](https://github.com/OctoSense-org/OctoSense-App-Hub).

2. **The starter does not get a developer to a running app.** The first-app guide requires building the Hub and reference host against sibling checkouts. Its template deliberately omits the Card, kit and screenshot. Developers are then directed into a separate authoring pipeline and must adapt external service/controller examples to the contained runtime. The signed release cannot be tested directly with the reference host because that host has no publisher-key option. Deliver a complete tiny app, bundled compatible runtime/kit, readable API reference and a development loop that exercises the same signed artifact path as production. Also reconcile “first submission signing is optional” with production `HostLimits::default()` requiring signatures. [First-app guide](../FIRST-APP.md), [delivery paths](../DEVELOPMENT.md), [reference host](../../crates/card-host/src/main.rs), [host defaults](../../crates/app-policy/src/policy.rs).

3. **Permissions are not a complete application SDK.** The store host reads `page.card`, data and kit, prepares a UI tree and renders it. It does not expose a general app script entrypoint simply because `.octoscript` files are allowed in a bundle. The sibling runtime's host-service bridge queues requests for an embedding host to answer, but no consumer of `take_splash_host_requests`/`splash_host_respond` was found in the reviewed Hub or mobile shell. The reference host prints an agent session profile instead of starting that session; the installed Card executor explicitly offers no assistant tools. Existing widget interactions and tested network callbacks are real, but do not establish functioning camera/location/shared-data services or arbitrary app business logic. Publish a per-platform capability matrix and wire only the supported services, with prompt failures for unsupported calls. For OctoSense's AI ecosystem, define app tools, context sharing, invocation and agent budget behavior as supported APIs. [Card loading](../../crates/appstore/src/lib.rs), [Card executor](../../crates/appstore/src/cardapp.rs), [reference agent handling](../../crates/card-host/src/main.rs), [host-service bridge](../../../makepad/widgets/src/splash_host.rs).

4. **The gate accepts a package that cannot run.** An isolated probe built a signed bundle containing no `page.card`, no kit, and text masquerading as the screenshot PNG. `check_bundle` passed. The gate checks extensions, paths, listing, digest and policy, but not the required executable shape, Card preparation or image decoding. A later optional scan can notice a missing Card, but is not an adequate mandatory admission check. Require the entrypoint and kit dependencies, parse and prepare the Card under the declared runtime, decode artwork with limits, and perform a minimal launch/interaction smoke check before approval. Keep author visual review distinct from automated validation. [Gate](../../crates/app-hub/src/gate.rs).

5. **Publisher continuity is bound to an ID string, not the recorded key.** The gate compares a new signature's `key_id` with the previous entry's `publisher`. Verification uses the externally supplied key mapping. The isolated probe supplied a different public key under the original publisher ID and signed v2 with it; the gate accepted it despite the stored v1 public key being different. This is not a demonstrated unauthorized remote publish—the current operator still controls publication—but it defeats the promised continuity boundary if submissions supply that mapping. Resolve update verification against the trusted publisher registry or previous entry, and make rotation/transfer a separate authenticated, audited operation. [Continuity check](../../crates/app-hub/src/gate.rs), [CLI key mapping](../../crates/app-hub/src/bin/hub.rs).

6. **An ordinary update disables the older installed version.** The probe installed signed v1, then accepted a catalog containing both offered v1 and offered v2. `Store::may_run` refused v1 with “update before running.” Mobile `Backend::may_open` delegates to that method, so this affects current shell launches. Normal publication should offer an update while preserving an approved installed version. Resolve launch policy and revocation against the installed version; resolve update availability separately. Only explicit version revocation should stop that version. Also define release ordering: version strings are currently opaque and newest means last appended, rather than a validated release sequence or semantic version. [Shared launch check](../../crates/app-hub/src/client.rs), [mobile launch check](../../../OctoSense-mobile/apps/app-hub/src/catalog.rs).

**Remaining lifecycle gaps**

- **Compatibility:** the manifest has no minimum runtime/SDK version, feature requirements or data schema version. Listing platforms are descriptive and the current mobile adapter does not enforce them. Adding unknown manifest fields is rejected, so design a deliberate schema migration. Resolve compatible releases on the device and test the supported OS/runtime matrix. [Manifest](../../crates/app-policy/src/manifest.rs), [listing](../../crates/app-policy/src/listing.rs).
- **Release control:** catalog status is only `Offered` or `Withdrawn`. There are no private beta audiences, channels, rollout percentages, scheduled publication, last-known-good selection or app-data migration contract. Mobile filesystem rollback on a failed installation already exists; functional rollback after a bad release is a different missing capability. [Catalog model](../../crates/app-hub/src/index.rs), [mobile replacement/recovery](../../../OctoSense-mobile/apps/app-hub/src/catalog.rs).
- **Current mobile UX:** no uninstall action was found in the mobile view/backend. Its presentation `Entry` also omits support/privacy URLs, age rating, license and tested platforms that the underlying listing already contains. Expose those fields and an actionable reporting path; do not require a new backend schema merely to display existing metadata. Automatic updates, install queues, download cancellation and resumable transfer are also absent. [Mobile entry](../../../OctoSense-mobile/apps/app-hub/src/catalog.rs), [mobile detail/actions](../../../OctoSense-mobile/apps/app-hub/src/view.rs).
- **Store operations:** catalog freshness is measured from its signed publication date, not the latest fetch. Installs stop after 14 days without a fresh signature, even if the static origin is reachable. No renewal workflow was configured. Add scheduled re-signing, monotonically increasing sequence, atomic release publication, protected signing, recovery and availability alerts. Define compromised-key revocation and publisher-key recovery as well as ordinary key rotation. Static hosting can remain the initial delivery system. [Freshness](../../crates/app-hub/src/client.rs), [signing](../../crates/app-hub/src/signing.rs).
- **Scale and support:** packages are base64 JSON fetched in a single request, and the full catalog is downloaded. This is workable for small bundles but offers no resume/delta/pagination path. Add measurements before changing the architecture. Provide per-release install/launch failure visibility and a developer issue channel early; advanced recommendations and commerce can follow real adoption. [Pack format](../../crates/app-hub/src/pack.rs), [HTTP client](../../crates/app-hub/src/remote.rs).
- **Admission ergonomics:** the text gate rejects every literal `https://` in Card/data/script/text content, even harmless displayed links or API endpoints for allowed hosts. Replace broad string checks with structured resource and effect validation, retaining runtime network enforcement. Publish clear supported limits: 8 MB packages, host storage/compute ceilings, and the distinction between a capability request and implemented functionality. [Asset-reference gate](../../crates/app-hub/src/gate.rs).

**Smallest useful developer experience**

These commands describe a proposed interface, not commands that exist today:

```sh
hub new my-app --template notes
cd my-app
hub dev                         # matching runtime, reload, logs and device preview
hub test                        # schema, permissions, rendering and interactions
hub login                       # establish publisher identity once
hub publish --channel beta      # build, validate, sign, upload and show status
hub promote 1.0.0 --to stable    # release the already-reviewed artifact
```

Use one project configuration with generated manifest/listing defaults, an SDK lockfile and explicit permissions. Keep signing mechanics behind the CLI, with secure key custody or CI identity and an escape hatch for developers managing their own keys. A GitHub Action should call the same supported API. Development should not require cloning framework repositories, operating Hub keys, manually editing the catalog or hand-assembling review packets.

Start with a runnable offline notes app, an API-backed app using test credentials, and an app demonstrating an implemented OctoSense tool/agent integration. Each example must complete a user action and preserve expected state after restart. A screenshot-only template is insufficient. Add an editor schema/completion package and precise errors with suggested fixes before building a large developer dashboard.

**Recommended delivery order and acceptance criteria**

1. **Make one outside developer successful.** Fix the reproduced gate, continuity and update defects; make core Card logic/services usable; ship a runnable template and installable SDK; add authenticated submissions, a protected review/release job, catalog renewal, and mobile uninstall. Demonstrate from a clean machine that a developer outside the organization can submit without repository write access, install on a clean device, use the app, publish v2 while v1 still opens, update without losing data, and uninstall. Suggested usability targets: first functioning preview in 15 minutes, first beta submission in 30 minutes excluding review time. Measure these with developers unfamiliar with the project.
2. **Make a small public beta maintainable.** Add runtime compatibility, signed device previews/private beta, review status and feedback, release promotion/rollback, migrations, publisher recovery/team roles, support/privacy/report links and release health diagnostics. Operate several independent apps through multiple releases and one deliberately failed update/revocation drill.
3. **Expand the marketplace when demand justifies it.** Add richer discovery, ratings/replies, localization and accessibility tooling, larger artifact delivery, and optional commerce. Decide separately whether native packages belong in App Hub. Paid-app parity requires a substantial entitlement/payment/settlement system; it should not delay proving the free Card-app workflow.

It can be rerun with `cargo run --offline --manifest-path target/store-readiness-probe/Cargo.toml` from the Hub repository.

The passing tests establish existing coverage, not store readiness. This review did not launch a new graphical/device session, test every OS, audit private infrastructure or conduct a comprehensive sandbox security assessment. Runtime/service conclusions are based on source tracing; deployment claims are limited to the public origin and repository APIs checked during this review. Existing mobile planning-file modifications were left intact.
